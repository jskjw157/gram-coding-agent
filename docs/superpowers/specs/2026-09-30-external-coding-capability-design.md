# Authenticated external coding capability (#159)

## Intent and constraints
The scheduler must hand Instructions, Analyze, and Modify to the existing authenticated MCP controller, while Gram owns task UUID, workspace, repository lease, mutation, verification and publication. No model SDK, credentials, new authentication grants, generic shell interface, fake success, or live acceptance is introduced. Runtime availability is not a claim of end-to-end production readiness.

## Design choice
Use a durable step/result rendezvous over the existing authenticated MCP route. An outbound worker would require a new credential/transport contract; an in-process model contradicts the approved architecture. Add `coding_step_get`, `coding_step_read`, `coding_step_submit`, and `coding_step_fail`. Each request carries task UUID and a unique step UUID. The step is bound locally to the recorded workspace ID/path/branch and the currently held task lease. IDs are correlation identifiers, not authentication tokens. Authentication remains the existing tunnel and internal-secret boundary; this runtime has one authenticated control-plane trust domain, not independently authenticated tenant owners.

The runner passes Task UUID explicitly when requesting Instructions. Each phase publishes one pending request and awaits the controller. Instructions exposes locally read root AGENTS.md (or a documented absence) and requires an exact digest acknowledgement. Analyze returns a nonempty summary and unique task-relative intended paths. Modify accepts nonempty exact patches for those paths, all preconditions checked before any write. Every read/write uses FileService/WorkspacePathGuard with a stricter capability policy: canonical ordinary source paths only; no Git metadata, symlinks, credential/config-sensitive paths or arbitrary executable commands. Patches require an exact old-content SHA256 and a changed replacement. No externally supplied Git SHA is trusted.

## Durable identity and replay
SQLite records step UUID, task UUID, workspace ID/path/branch, phase, process-run UUID, timestamps and terminal state only; no file contents, controller output, or secrets. A compare-and-set claims a PENDING step before output can be applied. Same-process reconnect re-reads the same pending request and may submit once. Duplicate, wrong-task, wrong-phase, expired, terminal, replaced-workspace, and previous-process step IDs fail closed before writes. Startup invalidates old pending/applying steps; tasks and repository locks remain for explicit existing recovery. Never transparently retry interrupted mutation. A crash between writes has an uncertain outcome and requires inspection/recovery; patches are not represented as a filesystem transaction.

## Lifetime and errors
Default step deadline is 30 minutes with validated configuration and testable timers. The independent RepoLock heartbeat continues while waiting. Controller failure/timeout rejects the runner; scheduler records FAILED, preserving the lock until confirmed push or existing explicit recovery. Shutdown first aborts pending capability waits, then drains the scheduler and quiesces held leases. No wait is silently converted into success. A canceled/changed task or lost lease is rejected on every operation and before mutation.

## Scope and verification
Implement repository, authenticated MCP schema/registration, app adapter, main composition and deterministic fixtures. Tests cover reconnect, retry/replay, concurrent submits, cross-task/workspace, restart, timeout/shutdown, lock loss, unsafe paths, stale patch content and real file mutation. Existing #158 snapshot verification/publication remains unchanged; this change does not add approval consumption (#151), repair, verification-plan orchestration, real-account execution, or Windows/WSL acceptance. #159 remains open until its complete live-control acceptance is demonstrated through the verified integration.
